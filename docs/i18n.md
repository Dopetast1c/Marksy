# Marksy localisation: interface languages and how to add one

Marksy ships in twelve interface languages and is built so that a thirteenth is one JSON file and one line in a list. The interface language is independent from the diary system: a family on the Belarusian provider can use the app in Polish, and a Dutch school's provider can be used in English.

## 1. Languages

| Code | Language | Native name | Plural forms (CLDR) | Decimal separator |
|---|---|---|---|---|
| `ru` | Russian | Русский | one, few, many, other | `,` |
| `be` | Belarusian | Беларуская | one, few, many, other | `,` |
| `uk` | Ukrainian | Українська | one, few, many, other | `,` |
| `kk` | Kazakh | Қазақша | one, other | `,` |
| `en` | English | English | one, other | `.` |
| `pl` | Polish | Polski | one, few, many, other | `,` |
| `de` | German | Deutsch | one, other | `,` |
| `es` | Spanish | Español | one, many, other | `,` |
| `pt` | Portuguese | Português | one, many, other | `,` |
| `fr` | French | Français | one, many, other | `,` |
| `nl` | Dutch | Nederlands | one, other | `,` |
| `ro` | Romanian | Română | one, few, other | `,` |

`en.json` is the source of truth for keys and the fallback for any missing string. `ru.json` is the second complete, human-reviewed file (the first family uses it). The other ten are added in milestone M5e (`docs/build-plan.md`), after the interface strings have settled; until then they have no file and every string falls back to English key by key. They start as careful machine translations reviewed by a native speaker when one joins; `locales/STATUS.md` records the review status per language so users know what to expect, and the app shows a small "help improve this translation" link in Settings for languages still marked `machine`.

Spelling note for Russian copy: the Belarusian language and the adjective are written «беларуский» / «Беларуская» (the country's own spelling), not «белорусский». Subject names that come from a diary are shown exactly as the diary sends them and are not touched.

## 2. Architecture

```
packages/i18n/
  src/languages.ts        the list above: code, native name, direction, date and number locale
  src/locales/en.json     source of truth
  src/locales/ru.json     ... one file per language, flat keys with dots: "overview.average"
  src/locales/STATUS.md   review status per language
  src/translate.ts        createT(locale, catalogs): plurals via Intl.PluralRules, {{x}} interpolation, English fallback
  src/index.ts            CATALOGS and translator(locale) for the server (notifications, Telegram, API error messages)
  src/check.ts            the rules of pnpm i18n:check as a pure function (a unit test runs them on every pnpm test)
  scripts/check.ts        pnpm i18n:check, see section 5
web/src/i18n/             react-i18next setup that imports the same JSON, language detector, Trans component helpers
```

- One package, two consumers. The web app uses `react-i18next`; the server uses a tiny `t()` from the same JSON for push and Telegram messages, digests and user-facing API errors. There is no second copy of any string.
- Plurals use i18next's built-in CLDR plural categories (`_one`, `_few`, `_many`, `_other` suffixes), which is what Russian, Ukrainian, Belarusian and Polish need. Interpolation is `{{count}}`; formatting inside strings is not allowed, formatting happens in code (next point).
- Dates, weekday names, months and numbers are never written into translation files. They come from `Intl.DateTimeFormat` and `Intl.NumberFormat` with the active locale, so 8.3 is "8,3" in Russian and "8.3" in English without anyone translating it. The grading scale's `format.*` functions take the locale for the same reason.
- One exception: the twelve **short month names** of compact dates ("12–18 окт", "1–8 ноя"), keys `date.monthShort.1` to `date.monthShort.12`, because Intl writes some of them with a dot ("окт.") that the design does not use. Every short date in the app goes through one formatter, `shortDate` and `shortRange` in `packages/core` (`marks/short-dates.ts`), with the language's own names when its file has all twelve and Intl's otherwise; the web app reads them from the current language's own file only (`dateStyle()`), so a language without them never shows English months. `en` and `ru` have them; a new language may add them.
- Keys are English, lower camel, grouped by screen or domain: `overview.average`, `feed.filter.tests`, `guidance.hint.upcomingTest.title`, `scale.by-10.band.critical`, `notify.newMark.body`. Key names describe the meaning, never the Russian wording.
- Content from the diary (subject names, lesson topics, homework, teacher comments) is data, shown as is. Work types, lesson types and mark kinds are enums in the canonical model and have keys (`workType.test`, `markKind.absent`).
- Grading scale labels (band names, scale names) are i18n keys referenced from the scale object, so a new language translates them in the same file as everything else.
- Text direction is a field on the language entry (`ltr` for all twelve); the shell sets `dir` on `<html>`, so a right-to-left language later needs no code change.

## 3. Choosing the language

Resolution order, first match wins:

1. The user's saved choice (`users.locale`), set from Settings or on the login screen. Any of the twelve languages, always.
2. For a new family, the provider's `languages.default` from its manifest (`ru` for `by-eschools`), because the people connecting that diary most likely read that language.
3. The browser's `navigator.languages`, matched to a supported code (`uk-UA` matches `uk`).
4. `en`.

A provider never restricts the language list. It can only influence two things: the default for new families and the order of the language picker. `languages.preferred` lists the languages to show first (for Belarus: `ru`, then `be`, the two official languages); the other ten follow in the fixed order of section 1. A Belarusian family that wants the whole app in English simply picks English.

The language is per Marksy user, not per family: a parent can use Polish while the child uses Belarusian. Notifications are sent in the recipient's language. Invite links carry the inviter's language as a hint for the first screen.

## 4. Writing strings so they translate

- No concatenation. Write whole sentences with placeholders: `"guidance.needMarks": "To reach {{final}} you need {{plan}}"`. The plan itself is built from keyed fragments (`"guidance.marksOf": "{{count}} × {{value}}"`) joined with a keyed separator (`"common.or": "or"`).
- One key per meaning, even when two Russian strings happen to coincide.
- Leave room. German and French run 20 to 30 percent longer than Russian; Finnish-style compound words can be longer still. Tab bar labels, chips and tile labels have a hard maximum (the five bottom tabs share 390 px) and their keys carry a `// max 11 chars` comment in `en.json` via a sibling `_comment` key. Components use `text-overflow: ellipsis` only as a last resort; the layout must fit the twelve shipped languages without it.
- Gender and case: avoid constructions that need them ("Кира получила" vs "Макс получил"). Write around the name: "Новая оценка у Киры" is a genitive the app cannot build; use "Кира: новая оценка 9 по алгебре".
- Numbers in copy follow the locale, so never type "8.3" into a string.

## 5. Tooling and checks

- `pnpm i18n:check` fails CI when: a key exists in `en.json` but is missing in another file (reported per language, so a missing key in a `machine` language is a warning, in `en` and `ru` an error); a file has a key `en.json` does not; a plural key lacks a category the language needs; a placeholder in a translation does not exist in the source.
- `pnpm i18n:extract` scans `web/` and `server/` for `t('...')` calls and reports keys used in code but absent from `en.json`, and keys present but unused.
- ESLint rule `i18next/no-literal-string` is on for `web/src` (JSX text and user-facing attributes) and for `server/src/notifications`. Test files and `providers/` are excluded; providers have no user-facing strings at all.
- A pseudo-locale `qps` (every string wrapped in brackets and lengthened by 30 percent) is available in development to catch overflow and missing keys at a glance.

## 6. Adding a language

1. Copy `packages/i18n/src/locales/en.json` to `<code>.json` and translate. Keep placeholders exactly. Add the plural categories your language needs; `pnpm i18n:check` tells you which.
2. Add one entry to `packages/i18n/src/languages.ts`: code, English name, native name, direction, and the BCP 47 tag to use for `Intl` (`'kk-KZ'`, `'pt-PT'` or `'pt-BR'`).
3. Add the language to `locales/STATUS.md` with your handle and the status `reviewed`.
4. Run `pnpm i18n:check` and `pnpm dev`, switch the language in Settings, open every screen with the pseudo-locale off and on; shorten what overflows in the tab bar and tiles.
5. Pull requests are not accepted: send a new translation or a correction as an issue (attach the JSON file or quote the strings). Translations are reviewed for completeness by the check and for quality by another speaker when one is available; a language can ship as `machine` or `reviewed`, and the status is visible in the app.

Belarusian, Kazakh and other languages whose school subject names differ from the diary's language are not a special case: the diary's subject names stay as the diary sends them, and only the interface changes.
