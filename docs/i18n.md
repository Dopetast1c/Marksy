# Marksy localisation: interface languages and how to add one

Marksy ships in twelve interface languages and is built so that a thirteenth is one JSON file and one line in a list. The interface language is independent from the diary system: a family on the Belarusian provider can use the app in Polish, and a Dutch school's provider can be used in English.

## 1. Languages

| Code | Language | Plural forms (CLDR) | Decimal separator |
|---|---|---|---|
| `ru` | Russian | one, few, many, other | `,` |
| `be` | Belarusian | one, few, many, other | `,` |
| `uk` | Ukrainian | one, few, many, other | `,` |
| `kk` | Kazakh | one, other | `,` |
| `en` | English | one, other | `.` |
| `pl` | Polish | one, few, many, other | `,` |
| `de` | German | one, other | `,` |
| `es` | Spanish | one, many, other | `,` |
| `pt` | Portuguese | one, many, other | `,` |
| `fr` | French | one, many, other | `,` |
| `nl` | Dutch | one, other | `,` |
| `ro` | Romanian | one, few, other | `,` |

Each language's own name (as the language picker shows it) is in `packages/i18n/src/languages.ts`.

`en.json` is the source of truth for keys and the fallback for any missing string. `ru.json` is the second complete, human-reviewed file (the first family uses it). The other ten were added in milestone M5e (`docs/build-plan.md`), after the interface strings had settled, as careful machine translations made with one glossary (`locales/GLOSSARY.md`: the word each language uses for each concept, and the choices a reviewer should know); a native speaker reviews one when they join; `locales/STATUS.md` records the review status per language so users know what to expect (the same status is the `status` of each language in `src/languages.ts`, a test keeps the two in step, and More says "translation not reviewed" (`lang.unreviewed`) under Language (`lang.title`) for any language that is not `source` or `reviewed`). For a language still marked `machine`, the language sheet ends with "Help with the translation" (`lang.help`): it opens the project's issue form for translations (`.github/ISSUE_TEMPLATE/translation.yml`, the language filled in; the project's address is the `repository` of the root `package.json`), which asks for the text with every name, mark, subject, comment or date replaced by a placeholder, and no real data in a screenshot or in text. The consent on "Connect a diary" (`login.mode.connect`) counts in English: in a `machine` language a line under it (`connect.consent.machine`) says that the translation is a machine one and the English text is the binding one, and shows the English text on a tap; the same consent version is accepted (`src/consent.ts`).

Spelling note for Russian copy: the Belarusian language and the adjective are written in the country's own spelling, not the older form; the exact words are in `locales/GLOSSARY.md`. Subject names that come from a diary are shown exactly as the diary sends them and are not touched.

## 2. Architecture

```
packages/i18n/
  src/languages.ts        the list above: code, native name, direction, date and number locale
  src/locales/en.json     source of truth
  src/locales/ru.json     ... one file per language, flat keys with dots: "overview.average"
  src/locales/STATUS.md   review status per language
  src/locales/_source.json  per language and key, the hash of the English text it was translated from (section 5)
  src/translate.ts        createT(locale, catalogs): plurals via Intl.PluralRules, {{x}} interpolation, English fallback
  src/pseudo.ts           the development pseudo-locale qps
  src/index.ts            CATALOGS and translator(locale) for the server (notifications, Telegram, API error messages)
  src/check.ts            the rules of pnpm i18n:check as a pure function (a unit test runs them on every pnpm test)
  scripts/check.ts        pnpm i18n:check [--strict], see section 5
  scripts/stamp.ts        pnpm i18n:stamp, see section 5
web/src/i18n/             react-i18next setup that imports the same JSON, language detector, Trans component helpers
```

- One package, two consumers. The web app uses `react-i18next`; the server uses a tiny `t()` from the same JSON for push and Telegram messages, digests and user-facing API errors. There is no second copy of any string.
- Plurals use i18next's built-in CLDR plural categories (`_one`, `_few`, `_many`, `_other` suffixes), which is what Russian, Ukrainian, Belarusian and Polish need. Interpolation is `{{count}}`; formatting inside strings is not allowed, formatting happens in code (next point).
- Dates, weekday names, months and numbers are never written into translation files. They come from `Intl.DateTimeFormat` and `Intl.NumberFormat` with the active locale, so 8.3 is "8,3" in Russian and "8.3" in English without anyone translating it. The grading scale's `format.*` functions take the locale for the same reason: the number of decimals is the scale's, the separator the language's. In the web app every number of the scale (averages, the previous period's value, goals, finals, band ranges) goes through one formatter, `web/src/lib/numbers.ts`, bound to the child's scale and the interface language; lint forbids calling core's formatters or `toFixed` anywhere else in `web/src`. Core's `format.test.ts` pins the writing per language, the scale snapshots (`by-10.snapshot.test.ts`) pin only values, and `web/src/lib/numbers.test.tsx` checks that Home, Attention, Subjects, Subject and Finals write the same number the same way in ru and en.
- One exception: the twelve **short month names** of compact dates ("12–18 Oct", "1–8 Nov"), keys `date.monthShort.1` to `date.monthShort.12`, because Intl writes some of them with a trailing dot in some languages (Russian among them) that the design does not use. Every short date in the app goes through one formatter, `shortDate` and `shortRange` in `packages/core` (`marks/short-dates.ts`), with the language's own names when its file has all twelve and Intl's otherwise; the web app reads them from the current language's own file only (`dateStyle()`), so a language without them never shows English months. `en` and `ru` have them; a new language may add them.
- Keys are English, lower camel, grouped by screen or domain: `overview.average`, `feed.filter.tests`, `guidance.hint.upcomingTest.title`, `scale.by-10.band.critical`, `notify.newMark.body`. Key names describe the meaning, never the Russian wording.
- Content from the diary (subject names, lesson topics, homework, teacher comments) is data, shown as is. Work types, lesson types and mark kinds are enums in the canonical model and have keys (`workType.test`, `markKind.absent`).
- Grading scale labels (band names, scale names) are i18n keys referenced from the scale object, so a new language translates them in the same file as everything else.
- Text direction is a field on the language entry (`ltr` for all twelve); the shell sets `dir` on `<html>`, so a right-to-left language later needs no code change.

## 3. Choosing the language

Resolution order, first match wins:

1. The user's saved choice (`users.locale`), set from Settings or on the login screen. Any of the twelve languages, always.
2. For a new family, the provider's `languages.default` from its manifest (`ru` for `by-eschools`), because the people connecting that diary most likely read that language.
3. The browser's `navigator.languages`, matched to a supported code (`uk-UA` matches `uk`).
4. `en`.

A provider never restricts the language list. It can only influence two things: the default for new families and the order of the language picker. `languages.preferred` lists the languages to show first (for Belarus: `ru`, then `be`, the two official languages); the other ten follow in the fixed order of section 1. A Belarusian family that wants the whole app in English simply picks English.

The language is per Marksy user, not per family: a parent can use Polish while the child uses Belarusian. Notifications are sent in the recipient's language. Invite links carry the inviter's language as a hint for the first screen.

## 4. Writing strings so they translate

- No concatenation. Write whole sentences with placeholders: `"guidance.needMarks": "To reach {{final}} you need {{plan}}"`. The plan itself is built from keyed fragments (`"guidance.marksOf": "{{count}} × {{value}}"`) joined with a keyed separator (`"common.or": "or"`).
- One key per meaning, even when two Russian strings happen to coincide.
- Leave room. German and French run 20 to 30 percent longer than Russian; Finnish-style compound words can be longer still. Labels with a fixed room have a hard maximum (the five bottom tabs share 360 px: 11 characters; the four period segments: 10), written as a sibling `_comment` key in `en.json` and enforced by the check (section 5). Components use `text-overflow: ellipsis` only as a last resort; the layout must fit the twelve shipped languages without it. The line under a list row may take two lines for the app's own words; only text that comes from the diary or the family (a topic, a teacher's comment, a subject's or a system's name) is cut to one line, and it sits in an element with `data-content` (the `subIsData` and `titleIsData` props), which the fit check of `pnpm smoke:ui` skips.
- Gender and case: avoid constructions that need them (in Russian, a past-tense verb agrees with the child's gender, and "a new mark of <name>" needs the name in a case the app cannot build). Write around the name: "<name>: new mark 9 in algebra".
- Numbers in copy follow the locale, so never type "8.3" into a string.

## 5. Tooling and checks

- `pnpm i18n:check` reports, per language: a key of `en.json` missing in another file; a translation that is **stale** (below); a plural key without a category the language needs. In `en` and `ru` these are errors, in a `machine` language warnings. Always errors, in every file: a key `en.json` does not have, a placeholder the source does not have, a value longer than its key's limit. The rules are a pure function (`src/check.ts`) that a unit test runs on the real files, so `pnpm check` fails on any error. `pnpm i18n:check --strict` fails on the warnings too; **it is green before every merge into `main`** (`docs/build-plan.md`, Definition of done).
- **Stale translations.** `src/locales/_source.json` records, per language and base key, a hash of the English text the translation was made from (all plural forms of the key together). When the English text of a key changes, every translation of it made from the old text is stale until it is translated again and stamped. A key never stamped counts as stale. Inside a milestone a machine language may lag (warnings); by the merge, the new and changed keys are translated into every language, only those keys, never whole files, and stamped: `pnpm i18n:stamp <lang|all> <key...>` (with or without a plural suffix), or `--every-key` for a whole new file. Stamp only what was actually translated or checked. `ru` is a complete language, so changing an English text without updating and stamping `ru` fails `pnpm check` at once.
- **Length limits.** A key whose text has a fixed room carries a sibling `"<key>_comment": "... max N chars"` in `en.json` (the bottom tabs: 11, the period segments: 10). The check holds every language to it; translations do not copy the `_comment` keys.
- ESLint rule `i18next/no-literal-string` is on for `web/src` (JSX text and user-facing attributes) and for `server/src/notifications`. Test files and `providers/` are excluded; providers have no user-facing strings at all.
- A pseudo-locale `qps` (`src/pseudo.ts`: every English string accented, lengthened by 30 percent and wrapped in brackets, placeholders kept) exists in development only, to catch overflow and strings that bypass `t()` at a glance. It is the last option of the language sheet in `pnpm dev`, and never part of a production build.
- **Development override.** In development, `localStorage['marksy.lang.override']` (set by the pseudo-locale option, or by `pnpm smoke:ui --lang <code>`) shows this device in a language without changing the user's saved one; picking a language in the sheet ends it. `pnpm smoke:ui` checks every shot for text cut by an ellipsis, spilling out of its box or making the page wider than the screen (a `WARN` line); with `--lang` such a line fails the run. Each language is checked with `pnpm smoke:ui --only seed --lang <code>`, and `qps`, `de` and `fr` before every merge that changes a screen.

## 6. Adding a language

1. Copy `packages/i18n/src/locales/en.json` to `<code>.json` and translate. Keep placeholders exactly. Add the plural categories your language needs; `pnpm i18n:check` tells you which.
2. Add one entry to `packages/i18n/src/languages.ts`: code, English name, native name, direction, and the BCP 47 tag to use for `Intl` (`'kk-KZ'`, `'pt-PT'` or `'pt-BR'`).
3. Add the language to `locales/STATUS.md` with your handle and the status `reviewed`.
4. Run `pnpm i18n:check` and `pnpm dev`, switch the language in Settings, open every screen with the pseudo-locale off and on; shorten what overflows in the tab bar and tiles.
5. Pull requests are not accepted: send a new translation or a correction as an issue (the Translation form for a few strings; attach the JSON file for a whole language). Translations are reviewed for completeness by the check and for quality by another speaker when one is available; a language can ship as `machine` or `reviewed`, and the status is visible in the app.

Belarusian, Kazakh and other languages whose school subject names differ from the diary's language are not a special case: the diary's subject names stay as the diary sends them, and only the interface changes.
